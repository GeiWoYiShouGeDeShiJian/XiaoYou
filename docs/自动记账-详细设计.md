## 1. 目标与范围

### 1.1 目标

| # | 目标 | 说明 |
|---|---|---|
| G1 | 双通道识别 | 无障碍 + 通知监听同时开启，互为备份：微信/支付宝支付页靠无障碍，支付宝/云闪付/美团/京东等带金额的通知靠通知监听 |
| G2 | 账单详情弹窗 | 用户点开微信/支付宝任意一笔账单详情时，弹出悬浮窗确认入账（核心诉求） |
| G3 | App 内总开关 | 设置页提供总开关与分通道、分应用开关，关闭后两通道完全停止解析 |
| G4 | 复用现有设施 | 去重（dedup_hash）、自动分类（KeywordMatcher）、入账（SaveTransactionUseCase）、通知（NotificationHelper）全部复用 |

### 1.2 范围内

- 无障碍识别：微信/支付宝的支付成功页、账单详情页、转账完成页、红包领取页
- 通知监听：支付类 App 通知（支付宝、云闪付、美团、京东、拼多多、抖音、银行动账通知）
- 三种入账模式：悬浮窗确认（默认）/ 通知确认 / 静默入账
- 历史账单：继续走现有 CSV 导入（CsvScreen），本方案不改动

### 1.3 范围外（远期可选）

- 截图 + 系统 OCR 兜底（微信部分页面节点树拿不到文本时）
- 无障碍自动翻页读账单列表做增量同步
- Xposed/LSPosed、短信读取（个人 sideload 可做但先不做，保持权限最小化）

## 2. 总体架构

```
微信/支付宝页面            支付类App通知
     │                        │
┌────▼─────────┐      ┌───────▼────────┐
│ 无障碍服务     │      │ 通知监听服务     │
│ Accessibility │      │ Notification   │
│ Service       │      │ ListenerService│
└────┬─────────┘      └───────┬────────┘
     │ AccessibilityNodeInfo树  │ Notification.Extras文本
     │                        │
┌────▼────────────────────────▼───────┐
│           AutoRecordPipeline         │
│  ① 总开关检查 ② 页面防抖/指纹         │
│  ③ 忽略名单过滤 ④ 解析为BillCandidate │
│  ⑤ dedupHash 入库查重                │
└────┬─────────────────────────────────┘
     │ BillCandidate(金额/商户/方向/单号/来源/建议分类)
     │
┌────▼──────────────────────────────┐
│           确认交互层                 │
│  模式A: 悬浮窗确认（默认）            │
│  模式B: 通知确认 → 预填记账页         │
│  模式C: 静默入账 + 可撤销通知         │
└────┬──────────────────────────────┘
     │ TransactionDomain(source = AUTO_*)
┌────▼──────────────────────────────┐
│ SaveTransactionUseCase.execute()   │
│ → TransactionRepository → Room     │
│ → BudgetNotificationScheduler      │
└────────────────────────────────────┘
```

设计原则：

- **两个入口服务只做"采集"**，拿到原始数据立刻交给 Pipeline，服务内不写业务逻辑，保证单个服务崩溃不影响另一个通道。
- **Pipeline 无状态化**（忽略名单/防抖缓存从 AppSetting 与内存 LRU 读取），便于测试。
- **入账只有一个出口** `SaveTransactionUseCase`，自动记账不绕过它，余额联动、预算触发、图片标签逻辑天然继承。

## 3. 通道一：无障碍服务

### 3.1 服务声明

`core/autorecord/AutoRecordAccessibilityService.kt`，`@AndroidEntryPoint`（Hilt 支持注入到 Service）。

Manifest 声明：

```xml
<service
    android:name=".core.autorecord.AutoRecordAccessibilityService"
    android:exported="false"
    android:label="@string/auto_record_service_label"
    android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">
    <intent-filter>
        <action android:name="android.accessibilityservice.AccessibilityService" />
    </intent-filter>
    <meta-data
        android:name="android.accessibilityservice"
        android:resource="@xml/auto_record_accessibility_config" />
</service>
```

### 3.2 服务配置 `res/xml/auto_record_accessibility_config.xml`

```xml
<accessibility-service
    android:accessibilityEventTypes="typeWindowStateChanged|typeWindowContentChanged"
    android:accessibilityFeedbackType="feedbackGeneric"
    android:accessibilityFlags="flagReportViewIds|flagRetrieveInteractiveWindows"
    android:canRetrieveWindowContent="true"
    android:isAccessibilityTool="true"
    android:notificationTimeout="300"
    android:packageNames="com.tencent.mm,com.eg.android.AlipayGphone"
    android:description="@string/auto_record_service_desc" />
```

关键决策：

| 配置 | 值 | 理由 |
|---|---|---|
| packageNames | 仅微信、支付宝 | 系统层白名单，其他 App 的事件根本不会送达本服务，隐私与性能双收 |
| typeWindowStateChanged | 监听 | 打开新页面（支付成功页/账单详情页）的主信号 |
| typeWindowContentChanged | 监听 | 页面内内容渐次加载（碰一碰动画、防抖延迟加载）时的补充信号 |
| notificationTimeout | 300ms | 事件节流，避免高频 CONTENT_CHANGED 打爆 CPU |
| isAccessibilityTool | true | 声明为无障碍工具后，Android 13+ 的无障碍设置页不再显示"非无障碍用途"红色警告与额外拦截弹窗。本 App 仅 sideload 分发、不上架 Google Play，无 Play 审核风险；API 31 以下系统自动忽略该属性 |

### 3.3 事件处理流程

```kotlin
override fun onAccessibilityEvent(event: AccessibilityEvent) {
    if (!pipeline.enabled()) return                      // App内总开关：关=直接丢弃，不做任何读取
    val pkg = event.packageName?.toString() ?: return
    when (event.eventType) {
        AccessibilityEvent.TYPE_WINDOW_STATE_CHANGED -> {
            pendingJob?.cancel()                         // 防抖：新页面打开时取消上一次抓取
            pendingJob = serviceScope.launch {
                delay(600)                               // 等600ms页面渲染稳定
                rootInActiveWindow?.let { pipeline.submitFromNodes(pkg, it) }
            }
        }
        AccessibilityEvent.TYPE_WINDOW_CONTENT_CHANGED -> {
            if (pipeline.isSamePageDebounced(pkg)) return  // 同页面1s内只处理一次
            rootInActiveWindow?.let { pipeline.submitFromNodes(pkg, it) }
        }
    }
}
```

- `onServiceConnected()`：初始化 Pipeline、上报服务已连接状态。
- `onUnbind()` / `onInterrupt()`：清理协程作用域。
- 全程 try-catch 包裹，单次解析异常只记日志，不抛出（防止系统因崩溃禁用服务）。

### 3.4 服务状态检测（供设置页与首页提示用）

```kotlin
fun isAccessibilityEnabled(context: Context): Boolean {
    val expected = ComponentName(context, AutoRecordAccessibilityService::class.java)
    return AccessibilityManager.getInstance(context)
        .getEnabledAccessibilityServiceList(AccessibilityServiceInfo.FEEDBACK_GENERIC)
        .any { it.resolveInfo?.serviceInfo?.let { s -> ComponentName(s.packageName, s.name) } == expected }
}
```

跳转开启：`Intent(Settings.ACTION_ACCESSIBILITY_SETTINGS)`。

### 4.1 服务声明

```xml
<service
    android:name=".core.autorecord.AutoRecordNotificationListener"
```

> 注：targetSdk 37 下该组件 exported 需为 true（系统要 bind 它），有系统权限保护，无安全风险。

### 4.2 处理逻辑

```kotlin
override fun onNotificationPosted(sbn: StatusBarNotification) {
    if (!pipeline.enabled()) return                                  // App内总开关
    if (sbn.packageName !in pipeline.notifyWhitelist()) return       // 分应用白名单
    if (sbn.isOngoing) return                                        // 常驻通知跳过
    val extras = sbn.notification.extras
    val title = extras.getCharSequence(Notification.EXTRA_TITLE)?.toString() ?: ""
    val text = (extras.getCharSequence(Notification.EXTRA_BIG_TEXT) ?: extras.getCharSequence(Notification.EXTRA_TEXT))?.toString() ?: ""
    pipeline.submitFromNotification(sbn.packageName, title, text, sbn.postTime)
}
```

### 4.3 支持的通知源（初版白名单，可在设置中增删）

| 包名 | App | 通知特征示例 | 金额可靠性 |
|---|---|---|---|
| com.eg.android.AlipayGphone | 支付宝 | "支付成功，付款12.50元" | 高 |
| com.unionpay | 云闪付 | "交易通知：消费¥36.00" | 高 |
| com.sankuai.meituan | 美团 | "支付成功，已支付¥25.80" | 高 |
| com.jingdong.app.mall | 京东 | "支付成功"（部分带金额） | 中 |
| com.xunmeng.pinduoduo | 拼多多 | "拼单成功，实付¥9.90" | 中 |
| com.ss.android.ugc.aweme | 抖音 | "支付成功 ¥xx" | 中 |
| 各银行App（可自选） | 工行/招行等 | "您尾号1234的账户支出100.00元" | 高 |

**微信通知刻意排除**：微信支付通知不带金额，识别了也没用，还占去重负担（vivo 也是这么处理的）。

### 4.4 系统授权跳转

## 5. 页面识别规则引擎

无障碍通道的核心。规则与代码分离，微信/支付宝改版时只需改规则表。

### 5.1 数据结构

```kotlin
data class PageRule(
    val id: String,                       // "wx_bill_detail"
    val packageName: String,
    val requiredMarkers: List<String>,    // 页面必须同时出现的特征词（全部命中才算该页面）
    val anyMarkers: List<String> = emptyList(), // 至少命中其一（可选加强）
    val amount: AmountExtractor,          // 主金额提取策略
    val direction: DirectionExtractor,    // 收支方向
    val merchant: MerchantExtractor,      // 商户名
    val orderNo: OrderNoExtractor,        // 交易单号（去重金标准）
    val tradeTime: TimeExtractor,         // 交易时间
    val billType: BillType                // EXPENSE/INCOME/TRANSFER/REFUND 候选
)
```

### 5.2 初版规则表

**微信（com.tencent.mm）**

| 规则 | requiredMarkers | 说明 |
|---|---|---|
| 账单详情页 | `["交易单号"]` + `["支付方式"]`（组合） | 用户点开账单列表某笔进入，含"商户全称""当前状态""交易时间" |
| 支付成功页 | `["支付成功"]` | 扫码/付款码支付完成页 |
| 转账完成页 | `["已转账"]` 或 `["朋友已收钱"]` | 转账场景 |
| 红包详情 | `["微信红包"]` + `["已存入零钱"]` | 收红包 → INCOME |

**支付宝（com.eg.android.AlipayGphone）**

| 规则 | requiredMarkers | 说明 |
|---|---|---|
| 账单详情页 | `["创建时间"]` + `["付款方式"]` | 账单列表点入，含"订单号""交易状态" |
| 支付成功页 | `["支付成功"]` + `["付款方式"]` | 扫码/付款完成 |
| 收款到账 | `["收款"]` + `["到账"]` | 收钱码收入 |

### 5.3 字段提取策略

**金额（最关键）**：

```kotlin
// 遍历节点树，收集所有匹配金额格式的文本节点
val moneyPattern = Regex("""[¥￥]?\s*\d{1,3}(?:[,，]\d{3})*(?:\.\d{1,2})""")
// 规则1：取 textSize 最大的命中节点（账单详情页主金额字号远大于其他）
// 规则2：过滤干扰——节点文本含"退款""优惠""券"的金额丢弃
// 规则3：金额为 0 或 > 100万 丢弃（明显非交易）
```

利用 `AccessibilityNodeInfo.textSize`（API 21+）区分主金额与"优惠券金额""退款金额"等次要金额，是准确率的关键。

**方向**：页面文本命中"收入|已存入|到账" → INCOME；命中"退款" → 退款候选（默认忽略并记日志，人工处理）；否则 EXPENSE。

**商户**：优先"商户全称："/"对方："标签节点的**相邻兄弟节点**文本；兜底取页面顶部第一个非金额文本节点。

**单号**："交易单号"/"订单号"标签的相邻节点值（微信详情页有，支付成功页可能没有 → 降级用模糊指纹，见第6节）。

**时间**："交易时间"/"创建时间"字段值，`yyyy-MM-dd HH:mm:ss` 解析；解析失败用当前时间。

**类型映射**：

| 识别结果 | TransactionType | 备注 |
|---|---|---|
| 普通支出 | EXPENSE | 分类由 KeywordMatcher(商户名) 建议 |
| 收入/红包 | INCOME | |
| 微信零钱→银行卡（提现） | TRANSFER | toAccountId 取用户配置的映射 |
| 退款 | 不自动入账 | 发通知提醒用户手动处理，避免与原单重复 |

### 5.4 节点遍历实现要点

- 用 `nodeInfo.findAccessibilityNodeInfosByText("交易单号")` 直接定位标签，再取 `parent` 遍历兄弟，比全树 DFS 提取准确。
- 全树 DFS 仅做金额收集（需要 textSize）与 markers 命中统计，控制遍历深度 ≤ 25 层，节点数上限 800，防性能失控。

## 6. 去重与忽略（三层防线）

双通道并存的最大风险是**同一笔交易被两个通道各记一次**，以及**用户反复查看同一账单详情反复弹窗**。

### 6.1 第一层：页面级防抖（内存）

- 指纹：`pkg + (单号 ?: 金额+商户+日期)`
- 同指纹 **10 分钟内**只处理第一次。内存 LruCache（容量 64）即可，进程重启清空无妨。

### 6.2 第二层：用户忽略名单（持久化）

用户在悬浮窗点"忽略本笔"后，指纹写入 AppSetting：

```
key = "auto_record_ignored"
value = JSON数组，FIFO 上限500条
```

再次识别到同指纹永不弹窗、不入账。

### 6.3 第三层：入库 dedup_hash 查重

自动记账专用指纹（与手动记账的 `accountId+tradeDate+amount+type` 规则共存于同一字段）：

```kotlin
fun autoDedupHash(c: BillCandidate): String {
    val input = if (c.orderNo != null) {
        "AUTO|${c.packageName}|${c.orderNo}"          // 有单号：绝对精确
    } else {
        "AUTO|${c.packageName}|${c.amount}|${c.merchant}|${c.dateyyyyMMdd}|${c.billType}"  // 无单号：模糊
    }
    return md5(input)
}
```

> **为什么不用现有 dedupHash 规则**：`accountId+tradeDate+amount+type` 会把"同一天同账户买两杯一样 15 元的咖啡"误判为重复。自动记账通道有交易单号这个更强的事实依据，应优先使用；两者格式同为 MD5 hex，写入同一 `dedup_hash` 列并走现有 `findByDedupHash` 查询，索引与 DAO 全部复用。

双通道冲突消解：通知先到、无障碍后到（或反之）→ 后到者 hash 查重命中直接丢弃，这正是 `AUTO|pkg|orderNo` 单号指纹的价值；无单号场景下模糊指纹（金额+商户+日期）也能覆盖绝大多数"同笔交易两通道都识别"的情况。

## 7. 确认交互层（悬浮窗/通知/静默）

### 7.1 三种模式（设置可选，默认弹窗确认）

| 模式 | 行为 | 适用 |
|---|---|---|
| A. 悬浮窗确认（默认） | 识别成功 → 悬浮窗弹出，展示预填信息，一键"记一笔" | 核心体验，用户核心诉求 |
| B. 通知确认 | 发通知，点通知进入预填好的记账页再确认 | 不喜欢悬浮窗/被支付保护拦截时降级 |
| C. 静默入账 | 直接入库 + 发"已自动记账（点击撤销）"通知 | 老手模式 |

### 7.2 悬浮窗实现

- 权限：`SYSTEM_ALERT_WINDOW`（Manifest 声明，API 26+ 用 `TYPE_APPLICATION_OVERLAY`；minSdk 24 走 `TYPE_PHONE` 分支）
- 检测：`Settings.canDrawOverlays(context)`；引导跳 `ACTION_MANAGE_OVERLAY_PERMISSION`
- Compose 内容挂载（关键骨架）：

```kotlin
class BillConfirmOverlay @Inject constructor(@ApplicationContext private val context: Context) {
    private var composeView: ComposeView? = null
    fun show(candidate: BillCandidate) {
        if (!Settings.canDrawOverlays(context)) { fallbackToNotification(candidate); return }
        val params = WindowManager.LayoutParams(WRAP_CONTENT, WRAP_CONTENT,
            if (Build.VERSION.SDK_INT >= 26) TYPE_APPLICATION_OVERLAY else TYPE_PHONE,
            FLAG_NOT_FOCUSABLE or FLAG_LAYOUT_NO_LIMITS, PixelFormat.TRANSLUCENT)
        val view = ComposeView(context).apply {
            setViewCompositionStrategy(ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed)
            setViewTreeLifecycleOwner(overlayLifecycleOwner)
            setViewTreeViewModelStoreOwner(overlayLifecycleOwner)
            setViewTreeSavedStateRegistryOwner(overlayLifecycleOwner)
            setContent { BillConfirmContent(candidate, ::confirm, ::ignore, ::dismiss) }
        }
        windowManager.addView(view, params)
    }
}
```

`overlayLifecycleOwner`：自定义 `LifecycleOwner + ViewModelStoreOwner + SavedStateRegistryOwner` 三合一。**初始化顺序是唯一的硬性约束**：`performRestore(null)` 必须在 Lifecycle 处于 INITIALIZED 状态时调用（即先于 `handleLifecycleEvent(ON_CREATE)`），顺序颠倒会抛 `performRestore can only be called in INITIALIZED state` 直接闪退。完整实现：

```kotlin
class OverlayLifecycleOwner : LifecycleOwner, ViewModelStoreOwner, SavedStateRegistryOwner {
    private val lifecycleRegistry = LifecycleRegistry(this)
    private val controller = SavedStateRegistryController.create(this)
    private val store = ViewModelStore()
    override val lifecycle: Lifecycle get() = lifecycleRegistry
    override val viewModelStore: ViewModelStore get() = store
    override val savedStateRegistry: SavedStateRegistry get() = controller.savedStateRegistry
    init {
        controller.performRestore(null)
        lifecycleRegistry.handleLifecycleEvent(Lifecycle.Event.ON_CREATE)
        lifecycleRegistry.handleLifecycleEvent(Lifecycle.Event.ON_RESUME)
    }
    fun destroy() {
        lifecycleRegistry.handleLifecycleEvent(Lifecycle.Event.ON_DESTROY)
        store.clear()
    }
}
```

dismiss 时调用 `destroy()` 并 `windowManager.removeView`。Hilt 依赖通过 `EntryPointAccessors.fromApplication(context, OverlayEntryPoint::class.java)` 获取（悬浮窗无法 @AndroidEntryPoint）。

### 8.4 受限设置解锁引导（Android 13+ 侧载应用必读）

**问题**：Android 13 起，非应用商店渠道安装（sideload APK）的应用，用户首次去系统设置开启"无障碍"或"通知访问"时会被系统拦截——开关置灰，或开启后提示"因安全原因，此应用受到限制"。这是系统针对侧载应用的反恶意软件机制，不是 App 的 Bug。

**解锁流程**（"允许受限设置"菜单只有先被系统拦截过一次才会出现，因此引导顺序不能反）：

1. 点"去开启"进入系统设置，尝试打开服务开关（触发系统的拦截记录）
2. 被拦截 → 返回桌面长按 App 图标 → 应用信息 → 右上角 ⋮ → 允许受限设置 → 确认
3. 重新进入无障碍/通知访问设置，此时开关已可正常打开

检测是否 sideload 安装（无障碍与通知通道共用）：

```kotlin
fun isSideloaded(context: Context): Boolean = try {
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.R) {
        context.packageManager.getInstallSourceInfo(context.packageName).installingPackageName == null
    } else {
        @Suppress("DEPRECATION")
        context.packageManager.getInstallerPackageName(context.packageName) == null
    }
} catch (_: Exception) {
    true
}
```

设置页"去开启"统一逻辑：

- 服务已开启（isAccessibilityEnabled / isListenerEnabled 为 true）→ 不再引导
- 商店安装（isSideloaded = false）→ 直接跳系统设置
- 侧载安装且服务未开启 → 弹三步引导对话框，提供"去尝试开启"（跳 ACTION_ACCESSIBILITY_SETTINGS / ACTION_NOTIFICATION_LISTENER_SETTINGS）与"去应用信息"（跳 ACTION_APPLICATION_DETAILS_SETTINGS）两个按钮

## 10. 保活与稳定性

### 10.1 现实预期

无障碍服务由系统绑定，**进程被杀 = 服务失效**。华为/荣耀最激进，钱迹也解决不了 100% 存活。策略是"引导 + 自检 + 快速恢复"。

### 10.2 措施清单

| 措施 | 实现 |
|---|---|
| 忽略电池优化 | `isIgnoringBatteryOptimizations()` 检测 + `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` |
| 常驻状态通知 | 无障碍连接后发低优先级常驻通知"自动记账运行中"（增强进程存活 + 用户可见状态，NotificationHelper 新渠道） |
| 自启动/后台锁定引导 | 保活引导页按厂商（小米/华为/OPPO/vivo）给图文步骤，纯文案不做机型误判 |
| 服务掉线自检 | MainActivity.onResume + 设置页进入时检测服务状态，掉线弹提醒；提醒中列明可能原因：进程被杀 / 系统重启 / 开启了高级保护模式（APM） |
| 高级修复授权（可选） | ADB 授予 WRITE_SECURE_SETTINGS 后，掉线自检可自动重开无障碍服务（见 10.3），参考钱迹"高级修复授权" |
| 通知监听 rebind | `onListenerConnected` 记录存活时间戳；掉线后**优先** `NotificationListenerService.requestRebind(ComponentName)`（API 24+ 官方 API，minSdk 24 全机型可用，温和恢复；仅对已授权监听器生效）；超 2 分钟未恢复再用组件 disable→enable 强制重绑（`PackageManager.setComponentEnabledSetting` 触发系统 PACKAGE_CHANGED 重新 bind，已验证的社区方案） |
| 解析崩溃保护 | Pipeline 全 try-catch，失败记日志继续运行 |

### 10.3 高级修复授权（可选，Phase 3）

参考钱迹"高级修复授权"：通过 ADB 一次性授予系统级权限 `WRITE_SECURE_SETTINGS`，之后当系统把无障碍关掉或弄坏时，App 可自动重新开启，减少手动去设置反复开关的次数。授权一次长期有效，不需要保持开发者模式或连接电脑：

```
adb shell pm grant com.example.jizhangruanjian android.permission.WRITE_SECURE_SETTINGS
```

```kotlin
fun ensureAccessibilityOn(context: Context) {
    if (context.checkSelfPermission("android.permission.WRITE_SECURE_SETTINGS") != PackageManager.PERMISSION_GRANTED) return
    val cn = ComponentName(context, AutoRecordAccessibilityService::class.java).flattenToString()
    val current = Settings.Secure.getString(context.contentResolver, Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES) ?: ""
    if (!current.split(':').contains(cn)) {
        Settings.Secure.putString(context.contentResolver, Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES, if (current.isEmpty()) cn else "$current:$cn")
    }
    Settings.Secure.putInt(context.contentResolver, Settings.Secure.ACCESSIBILITY_ENABLED, 1)
}
```

设置页"保活引导"提供"高级修复授权"入口：未授权时显示 ADB 命令复制按钮与电脑操作说明；已授权后由掉线自检自动调用。

## 11. 隐私与安全边界

| 边界 | 落实方式 |
|---|---|
| 只读支付相关内容 | 无障碍 XML `packageNames` 限定微信/支付宝，系统层屏蔽其他 App；通知白名单过滤；页面规则未命中不解析节点内容 |

| 随时可关 | 设置页一键关总开关；系统无障碍开关独立于 App 存在 |

|---|---|---|---|
| 1 | Room 迁移写错，或忘记在 DatabaseModule 注册 MIGRATION_18_19 | 启动即闪退，严重时数据库损坏 | 动手前先用 App 内备份/导出 CSV 留底；本迁移仅"加一列带默认值"属最低风险，但必须确认注册后才运行 |
| 2 | OverlayLifecycleOwner 初始化顺序颠倒 | 悬浮窗一弹就闪退 | performRestore 必须先于 ON_CREATE 调用（见 7.2 完整实现），照抄，不要自行调整顺序 |
| 3 | 无障碍服务内异常未捕获 | 系统可能直接禁用服务且无任何提示，表现为"自动记账突然全不工作" | onAccessibilityEvent 与 Pipeline 全 try-catch 是硬要求 |
| 4 | 悬浮窗里用常规 Hilt 注入 | 运行时注入崩溃 | 悬浮窗必须走 EntryPointAccessors（见 7.2）；Service 才能用 @AndroidEntryPoint |

### 15.2 容易误判为"代码坏了"的现象

| # | 现象 | 真实原因 |
|---|---|---|
| 1 | 开了开关但完全不弹窗 | 受限设置未解锁（8.4）/ 总开关或通道软开关没开 / 厂商手机管家杀了后台 |
| 2 | 微信某个页面识别不到 | 微信改版导致规则失效，属正常损耗，查识别日志（8.3）定位 |
| 3 | 悬浮窗弹不出来 | 华为/荣耀"支付保护"拦截，已设计降级为通知确认（7.4），不是 Bug |
| 4 | 重启手机后服务失效 | 厂商自启动管理，走保活引导（10.2），行业共性问题（钱迹同样） |

### 15.3 实施纪律

1. 一次只做一个 Phase，每写完一个文件先编译通过再写下一个；一口气全写完再编译，报错会成片，极难定位。
2. 验收必须用真机：模拟器的通知行为、无障碍节点树、厂商杀后台逻辑与真机差异极大。
3. 永远不要给 App 加 INTERNET 权限：本方案的隐私承诺建立在"无网络权限"之上（第 11 节），加了就破坏边界。
4. 静默入账（模式C）最后再开：识别错误会直接进账，先让悬浮窗确认模式（模式A）稳定运行一段时间。
5. 遇到依赖或构建问题，先比对 `gradle/libs.versions.toml` 版本目录约定，不要在模块里手写版本号。
